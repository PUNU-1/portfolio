# 03. Демо интеграции приёма оплаты в сайт

> **Демо-проект. Реальные платежи не проходят.** Товары вымышленные, «оплата» — заглушка: деньги не списываются, данные карты нигде не вводятся. Такая же пометка есть на каждой странице магазина.

## Какую задачу бизнеса решает

Малому бизнесу нужен сайт, где можно заказать и оплатить онлайн, а не «напишите в личку, пришлём реквизиты». Главная сложность не в кнопке «Оплатить», а в том, что вокруг неё: заказ нужно сохранить, понять, оплачен он или нет, не потерять и не обмануться.

Здесь собран именно этот каркас на трёх тестовых товарах:

- каталог, корзина, оформление заказа;
- заказ со статусами **создан → оплачен / ошибка**, повторная попытка оплаты после ошибки;
- **платёжный адаптер**: сейчас подключена заглушка «тестовая оплата», а настоящую систему можно подключить, не переписывая магазин (см. ниже);
- **webhook с проверкой подписи**: заказ становится «оплачен» только по подтверждению от платёжной системы, а не потому что покупатель вернулся на страницу «Спасибо».

## Как запустить

Нужен Python 3.10+.

**Windows:** двойной клик по `start.bat`. **Mac / Linux:** `bash start.sh`.

Скрипт сам создаст окружение, поставит зависимости и запустит сервер. Откройте в браузере <http://127.0.0.1:5050>.

Попробуйте: добавьте товары в корзину → «Оформить» → на странице «банка» нажмите «Имитировать отказ» (заказ станет «Ошибка оплаты») → «Попробовать оплатить снова» → «Имитировать успешную оплату».

Токены и ключи здесь не нужны. Настройки — в `.env` (создаётся из `.env.example`).

```
   │  POST /api/orders     │                                   │
   ├──────────────────────►│ считает сумму по каталогу,        │
   │                       │ сохраняет заказ (created),        │

   │◄── payment_url ───────┤◄──────────────── ссылка на оплату ┤
   │                                                           │
   ├──────────── покупатель платит на странице провайдера ────►│
   │                                                           │
   │                       │◄── POST /webhooks/payment ────────┤ подписанное уведомление

   │                       │   проверка подписи и времени      │

   │                       │   проверка платежа и суммы,       │
```


### Что защищено и как

| Риск | Что сделано |
|---|---|
| Покупатель подменил цену в браузере | Цену берёт сервер из каталога, цены из запроса игнорируются |
| Кто-то прислал поддельный webhook «оплачено» | Подпись HMAC проверяется по сырому телу запроса, сравнение за постоянное время |
| Перехваченный webhook отправили повторно позже | Метка времени входит в подпись, старше 5 минут — отказ |
| Провайдер прислал одно событие дважды | `event_id` запоминается, повтор не меняет данные |
| Подлинный webhook, но сумма не та | Сумма платежа сверяется с суммой заказа, иначе отказ |
| Платёж «чужого» заказа | Проверяется связка платёж ↔ заказ |
| Перебор чужих заказов | В ссылках случайный код (`public_id`), а не номер 1, 2, 3; email покупателя в API не отдаётся |
| Секреты в коде | Секрет подписи читается из `.env`; тест проверяет, что его нет в исходниках |

## Как подключить реальную платёжную систему

Магазин общается с оплатой только через интерфейс `PaymentProvider` ([`app/payments/base.py`](app/payments/base.py)). Из двух методов:

```python
class PaymentProvider(ABC):
    def create_payment(self, order_public_id, amount_kop, description, return_url) -> PaymentSession: ...
    def parse_webhook(self, headers, body) -> PaymentEvent: ...
```

Шаги:

1. **Договориться с провайдером** (ЮKassa, CloudPayments, Stripe и т.п.). Для приёма реальных денег провайдер требует определённый статус получателя (самозанятый, ИП, юрлицо) и проверяет данные, это делается в личном кабинете, а не в коде. Условия и комиссии у каждого свои. Вопросы по налогам и чекам (в России — по закону о применении ККТ) уточните у провайдера и бухгалтера.
2. **Получить ключи** в личном кабинете (идентификатор магазина, секретный ключ) и положить в `.env`, например `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`. Ключи не должны попасть в git.
3. **Написать класс-адаптер** `app/payments/<имя>.py`:

   ```python
   class MyProvider(PaymentProvider):
       name = "my_provider"

       def create_payment(self, order_public_id, amount_kop, description, return_url):
           # 1. Запрос к API провайдера «создать платёж»: сумма, валюта, описание, return_url,
           #    в метаданные положить order_public_id; добавить ключ идемпотентности.
           # 2. Из ответа взять id платежа и ссылку на страницу оплаты.
           return PaymentSession(payment_id=..., payment_url=...)

       def parse_webhook(self, headers, body):
           # 1. Проверить подлинность так, как требует провайдер (см. ниже). Не прошло — raise InvalidWebhook.
           # 2. Привести событие к PaymentEvent: event_id, status ("succeeded"/"failed"),
           #    payment_id, order_public_id, amount_kop.
           return PaymentEvent(...)
   ```

4. **Подключить** одной веткой в `get_provider()` ([`app/payments/__init__.py`](app/payments/__init__.py)) и поставить `PAYMENT_PROVIDER=my_provider` в `.env`. Страница «банка» (`fake_gateway`) регистрируется только для заглушки, лишнего удалять не нужно. Остальной код (заказы, статусы, идемпотентность, проверка суммы) работает как есть.
5. **Указать адрес webhook** в личном кабинете провайдера: `https://ваш-домен/webhooks/payment`. Нужен публичный HTTPS-адрес. Для проверки с домашнего компьютера используйте туннель (например, ngrok или cloudflared).
6. **Пройти заказ в тестовом режиме провайдера** (у большинства есть тестовые ключи и тестовые карты) и только потом включать боевые ключи.

Проверка подлинности webhook **у провайдеров разная**, смотрите их документацию. По моим сведениям: у Stripe подпись — в заголовке запроса (HMAC), у CloudPayments тоже HMAC в заголовке, а у ЮKassa подписи в уведомлении нет: рекомендуется проверять IP-адрес отправителя и запросить статус платежа напрямую через API. Принцип один: **не верить телу webhook на слово**. В заглушке показан вариант с HMAC.

Правила, которые нужно сохранить при любом провайдере:
- «оплачен» ставить только по проверенному webhook (или по ответу API провайдера), а не по возврату покупателя на сайт;
- отвечать на webhook кодом 2xx только когда событие действительно записано;
- сверять сумму и привязку платежа к заказу;
- обрабатывать повторные доставки.

> В этой сборке реальные провайдеры не подключались и не проверялись. Описание выше — схема, а не готовая интеграция.

## Ограничения (честно)

- Это учебный каркас, а не готовый интернет-магазин: нет личного кабинета, доставки, учёта остатков, писем покупателю, админки и защиты от массового создания заказов (нужен лимит запросов).
- Данные в SQLite. Для реального магазина нужна резервная копия базы.
- Сервер запускается встроенным сервером Flask: годится для демо. Для публикации используйте `gunicorn`, например `gunicorn "app.server:create_app()"`. **Если запускаете несколько процессов, обязательно задайте `PAYMENT_WEBHOOK_SECRET` в `.env`**, иначе у каждого процесса будет свой случайный секрет, и подписи заглушки не сойдутся. Публикация на хостинге в этой сборке не проверялась.
